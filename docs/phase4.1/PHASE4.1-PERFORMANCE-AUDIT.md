> 本阶段只做审计、真实测试与方案制定：**未修改任何生产代码、未改变数据库结构、未引入 npm 依赖、未改变现有功能**。
> 全部性能数据来自本机真实测试（Edge headless + IndexedDB + 真实生产模块），无估算数据。

- 生成时间：2026-11-14（Asia/Shanghai）
- 审计对象：FlowDay v0.3.0（IndexedDB 单文档架构）
- 测试脚本：`scripts/bench-4.1.mjs`、`scripts/bench-4.1b.mjs`、`scripts/bench-4.1c.mjs`、`scripts/bench-4.1-reload.mjs`、`scripts/merge-4.1.py`
- 原始数据：`docs/phase4.1/perf-raw.json`（合并稿）、`perf-raw-run1-storage-app.json`、`perf-raw-detail.json`、`perf-raw-modules.json`、`perf-raw-reload-prod.json`
- 对比表：`docs/phase4.1/perf-table.csv`；汇总：`perf-summary.json`

## 0. 结论先行（一页版）

1. **存储层不是瓶颈。** 10,000 条任务 = 2.0 MB JSON，整份读取中位 **33.2 ms**、整份写入中位 **33–54 ms**、空写事务（2 MB）约 **36 ms**。即便规模到 10k，IndexedDB 仍远未成为限制项。
2. **真正的瓶颈是渲染层。** 10,000 条任务时：搜索 UI 端到端 **2,646.9 ms**，优先级筛选 **5,634 ms**，状态筛选 **4,636.9 ms**；而同一批筛选的纯计算只有 **0.7–16.7 ms**。端到端时间里 **>95% 花在 React 渲染 8,000 个列表行上**。
3. **单条任务修改的端到端延迟**在 10k 时中位 **8,202 ms**（其中"点击 → 开始写库"4,777 ms，"写库"3,425 ms 为被主线程阻塞的观测值；独立测量写事务仅 33–54 ms）。1k 时中位 921 ms，5k 时 2,328 ms。
4. **页面重载**：开发服务器（未打包 ESM）中位 409 / 360 / 453 ms；**生产构建**中位 **106 / 120 / 192 ms**（1k/5k/10k）。生产环境下首屏并不是主要问题。
5. **一致性**：在 5,000 条规模下，4 个场景 × 5 次全部通过（含"防抖窗口内 (<180ms) 立即离开页面"），`pagehide` 补写有效，未复现丢数据。
6. **明确结论：Phase 4.2 不拆分 Object Store。** 拆分原型在所有列表类查询上更差（open 查询 468 ms、搜索 220 ms、计数 174 ms、10k 全量写 4,432 ms），单文档 + 内存计算在 FlowDay 的访问模式下更优。
7. **Phase 4.2 应优先做**：① 任务列表虚拟滚动/分页渲染（P0）；② 行组件 memo + 分组/排序缓存（P0）；③ Dashboard 统计单遍聚合（P1）；④ 搜索防抖与结果上限（P1）；⑤ 写入合并/批量 API（P2）。做完 ①② 后按同一套脚本复测，再决定是否需要架构级调整。

### 1.2 隔离措施（不触碰用户真实数据）

- 每一轮测量使用**独立临时 Chromium 用户配置目录**（`flowday/.tmp/bench-edge-profile*`），结束即删除；与用户真实浏览器 profile（含其 `flowday-db`）完全隔离。
- 存储层基准使用**独立数据库** `flowday-bench-4-1`（及拆分原型 `flowday-bench-split-4-1`）；应用级测量使用临时 profile 内的 `flowday-db`，仅在临时 profile 中存在。
- 每轮写库前先删除测试库，保证冷写入；应用级每次测量前先写入测试数据并**回读校验任务数**（防止上一次写回覆盖造成假数据）。

### 1.3 计时口径

- 统一使用页面内 `performance.now()`；含事务创建、提交、结构化克隆（IndexedDB 真实成本）。
- 存储层：先删除库 → 打开 → 写入/读取/更新，直接以 `performance.now()` 差值计时。
- 应用级 UI：输入/点击事件派发 → 等待 2 次 `requestAnimationFrame` 后读取行数，代表"用户操作到界面稳定"的端到端时间（含筛选、排序与 React 渲染）。
- 持久化分解：在页面加载前 HOOK `IDBObjectStore.put` 与 `transaction complete`，记录"点击 → 写入开始（含 React 渲染 + 180 ms 防抖）"与"写入开始 → 事务完成"两段，避免轮询读库的干扰。
- 重载就绪：`Page.navigate` 到 `/today` 后，页面内检测 `main` + `[data-fd-stats]` 出现的时间（`performance.now()`，相对导航开始）。

### 1.4 数据构造（确定性）

- 任务数 N = 1,000 / 5,000 / 10,000；日期覆盖 [-20, +39] 天轮转；P1–P3 轮转；每 5 条已完成 1 条；1/3 带备注；1/4 带时间与 60 分钟时长；分类 3 个轮转；1/9 来源 `ai`。

### 1.5 重复次数

- 记录中位数与最大值（原始 JSON 保留全部 5 次样本）。
- 补充测量（真实模块函数）同样 5 次取中位。

## 2. 当前架构审查

### 2.1 数据结构与规模

`AppData`（`src/types.ts`）为单文档结构：

| 实体 | 字段规模 | 说明 |
|---|---|---|
| `tasks` | N（1k/5k/10k） | 主要数据量来源，单条约 210 字节 |
| `settings` | 1 | 昵称、主题、周起始、AI 开关、demo 标记 |
| `projects` | 3 | 工作/学习/生活 |
| `habits` | 3 | 习惯定义 |
| `habitLogs` | N/10 | 打卡记录（当前量级很小） |

实测 JSON 体积与均摊：**204 KB / 1,026 KB / 2,053 KB**；单任务均摊约 **209–210 字节**（1k/5k/10k 基本一致，说明结构稳定）。

`navigator.storage.estimate()`（测试库）占用：1k ≈ 6.0 MB、5k ≈ 3.3 MB、10k ≈ 4.1 MB（浏览器统计包含索引/日志等开销，非线性的绝对值仅供参考；配额约 10.7 GB，远未接近）。

### 2.2 写入链路（每次状态变化都会整份写入）

```
dispatch(Action)
  → useReducer 产生新 AppData
  → AppStore useEffect([data])   （src/store/AppStore.tsx:87-98）
  → 180ms 防抖 timer（SAVE_DEBOUNCE_MS = 180）
  → saveAppData(data) → putState(data)   （src/lib/storage/db.ts:101-106）
  → 新事务 + os.put({schemaVersion, updatedAt, data}, 'state') + tx.oncomplete
页面隐藏：pagehide / visibilitychange 再补写一次（AppStore.tsx:100-115）
```

**结论：是。** 每一次"已提交的状态变化"都会触发**整份 AppData 的结构化克隆 + 单条记录整份写入**；30 秒内连续编辑在 180 ms 窗口内会被合并，但窗口结束后每次仍写全量（写放大 = 当前数据总量）。

### 2.3 读取链路（启动）

```
initializeStorage()（src/lib/storage/index.ts）
  → getState()          整份记录 structured clone（10k ≈ 33 ms）
  → migrateStoredState() schema 校验/规范化（10k ≈ 4.8 ms）
  → sanitizeImportedData() 全量 map/兜底（10k ≈ 7.1 ms）
  → React 首屏（Dashboard 渲染 + 统计）
```

### 2.4 事务模式与异常处理

- `db.ts` 的 `store()` 每次读写都**新建一个事务**（`db.transaction(name, mode)`），没有事务复用或批量写入 API。
- 异常处理完备：`onerror`/`onabort` 拒绝、`open` 超时 8 s、`onblocked` 明确报错、`onversionchange` 主动关闭连接；失败由上层 Toast 提示并停止持久化。
- **补充测量**（10k 数据）：每个"整份 readwrite 事务"（2 MB put）平均 **36.0 ms**；单游标读 **2.7 ms**；一次 `getState` 真实模块调用中位 **33.2 ms**。

### 2.5 渲染链路（真正的瓶颈）

- `TasksPage` 默认分组渲染**全部未完成任务**（已完成为前 20 条），无虚拟列表/分页。10k 任务时 DOM 中约 **8,000 行**任务（每行约 10 个节点）。
- 每一次筛选/搜索/勾选都触发整页 React 重渲染，并重复执行：
  - `sortTasks`（10k 中位 **49.5 ms**，含数组拷贝与比较器）
  - `last7DayCompletion`（**22.6 ms**）、`todayStats`（**2.5 ms**）、`focusTasks`（**13.5 ms**）
  - `groupedRenderPrep` 等价分组排序（实测 **45.6 ms**）
- 搜索为全量 substring（`title + notes`），无索引，但纯计算只 **15.8 ms**（10k），不是主要成本。

### 2.6 序列化/校验成本（真实模块，5 次中位）

| 操作 | 1k | 5k | 10k |
|---|---|---|---|
| JSON.stringify（整份） | 0.8 ms | 4.4 ms | **8.5 ms** |
| JSON.parse（整份） | 1.8 ms | 9.0 ms | **17.7 ms** |
| `sanitizeImportedData`（启动/导入校验） | 1.2 ms | 3.2 ms | **7.1 ms** |
| `parseImportedData`（导入路径） | 3.1 ms | 14.2 ms | **28.5 ms** |
| `validateBackup`（备份导入校验） | 4.5 ms | 19.8 ms | **33.7 ms** |

## 3. 数据规模性能对比（关键指标）

> 全部为真实测量，5 次中位/最大（单位 ms）。UI 列 = 开发态端到端（含渲染）；生产重载为 `vite preview`。

| 任务数 | JSON | 首次写入 med/max | 整份读取 med/max | 单条更新（存储层） | 顺序 20 写 | 批量 20 写 | 重载(dev) | 生产重载 | 搜索 UI | 优先级筛选 UI | 状态筛选 UI | 勾选端到端 | 其中写库 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 1,000 | 204 KB | 15.6 / 18.5 | 6.0 / 34.0 | 9.1 | 214.7 | 57.9 | 409.5 | **106.3** | 467.2 | 953.4 | 715.4 | 921.3 | 14.3 |
| 5,000 | 1,026 KB | 43.7 / 116.3 | 18.6 / 21.6 | 49.0 | 947.2 | 313.6 | 359.6 | **119.5** | 1,361.6 | 2,309.1 | 2,531.7 | 2,327.6 | 171.7 |
| 10,000 | 2,053 KB | 54.4 / 147.3 | 31.9 / 34.1 | 68.6 | 1,350.3 | 497.5 | 452.8 | **191.9** | 2,646.9 | 5,634.0 | 4,636.9 | 8,202.0 | 3,424.6\* |

\* 10k 的"写库"观测值包含主线程被 8,000 行渲染阻塞导致的 `tx.oncomplete` 回调延迟；**独立测量的写事务本身仅 33–54 ms**（见 2.4）。"勾选端到端"反映用户真实感受到的延迟。

补充：真实模块函数耗时（10k，5 次中位）：`sortTasks` 49.5 ms、`todayStats` 2.5 ms、`last7DayCompletion` 22.6 ms、`focusTasks` 13.5 ms、`filterTasks(query)` 15.8 ms、`filterTasks(priority)` 16.7 ms、`filterTasks(status=done)` 6.9 ms、`filterTasks(date=today)` 0.8 ms；`getState` 33.2 ms、`putState` 33.2 ms。

### 结论解读

- **存储层随规模近线性增长**（读 6 → 18.6 → 31.9 ms；写 15.6 → 43.7 → 54.4 ms），10k 仍属低风险区间。
- **UI 端到端超线性增长**（搜索 467 → 1,362 → 2,647 ms；筛选 953 → 2,309 → 5,634 ms），与"渲染行数 × 重渲染次数"一致，与"存储"关系很小。
- **顺序 20 次写（1.35 s at 10k）vs 批量 20 次写（0.50 s）**：批量事务可减少约 63% 写耗时，但仍是次要优化。

## 4. 一致性测试（刷新 / 关闭 / 切换标签页）

规模 5,000 条任务；每个场景 5 次；仅在"确认任务已进入内存状态"后开始计时（避免创建失败的假阴性）。

| 场景 | 通过 | 说明 |
|---|---|---|
| 创建后 **30 ms 内**立即离开页面（< 180 ms 防抖窗口） | **5/5** | `pagehide` 补写生效 |
| 创建后等待 500 ms 再离开 | **5/5** | 防抖窗口正常写入 |
| 修改已有任务后 30 ms 内立即离开 | **5/5** | 与上同机制 |
| 切换标签页（新开标签→返回）后刷新 | **5/5** | 数据一致 |

> 说明：首轮脚本的同类测试因未校验"创建是否成功"出现 2 次假阴性（创建动作本身未完成被计为丢失），已在补充轮修正；以本节 5/5 结果为准，首轮数据保留在 `perf-raw-run1-storage-app.json` 的 `consistencyRun1Superseded` 中备查。
> 未覆盖：强制结束浏览器进程/断电（`pagehide` 不会触发）的极端场景。

## 5. 架构原型对比：单文档（现状） vs 拆分 Store + 索引

原型实现（仅用于测量，未进入生产代码）：`tasks`（索引 `date`/`completedFlag`/`projectId`/`createdAt`）、`habits`、`habitLogs`（复合主键）、`settings`、`meta`。

| 操作（10k 数据） | 现状：单文档 + 内存计算 | 拆分 Store + 索引 | 结论 |
|---|---|---|---|
| 全量写入（一次事务） | **54.4 ms** | **4,432.5 ms** | 拆分后写入慢约 81× |
| 读取整份状态 | **31.9–33.2 ms** | —（需分查询） | — |
| 今日任务（index date） | 读 32 + 过滤 1.8 ≈ **34 ms** | 15.9 ms | 拆分略优 |
| 未完成任务（index completedFlag） | 读 32 + 过滤 1.2 ≈ **33 ms** | **468.5 ms** | 拆分差 14× |
| 按项目筛选 | 读 33 + 过滤 ≈ **34 ms** | **114.1 ms** | 拆分差 3.4× |
| 标题搜索（无索引，全表） | 读 33 + 计算 15.8 ≈ **49 ms** | **219.9 ms** | 拆分差 4.5× |
| 未完成计数 | 读 33 + 计数 2.5 ≈ **35 ms** | **173.8 ms** | 拆分差 5× |
| 单条记录更新 | 读+写 ≈ **66 ms** | **2.1 ms** | 拆分优（但不是当前瓶颈） |
| 分页 50 条（游标） | 读整份 33 ms | **7.8 ms** | 拆分优（当前无分页需求） |

**原因**：FlowDay 的列表页/统计/搜索几乎都需要"全部任务"；拆分后每个界面要发起多次索引查询并把结果拼回，单次 `getAll` 返回数千条结构化克隆对象（`open` 查询 468 ms 即 8,000 条记录的克隆成本），反而比一次 2 MB 整份读取（32 ms）更贵；而索引维护让批量写入从 54 ms 涨到 4.4 s（10k 记录 × 4 索引）。

## 6. 瓶颈排名（基于实测）

| 排名 | 瓶颈 | 实测证据 | 影响 |
|---|---|---|---|
| **1** | 任务列表全量渲染（无虚拟化/分页） | 10k：筛选 UI 4.6–5.6 s，纯计算仅 0.7–16.7 ms；DOM 约 8,000 行 | 用户可感知卡顿，任何筛选都慢 |
| **2** | 任意状态变化触发整页重渲染 | 10k：勾选端到端 8.2 s（写库独立仅 33–54 ms） | 点一次完成等数秒 |

| **7** | 每次操作新建事务，无批量 API | 整份 readwrite 事务平均 36 ms | 与 #4 叠加 |

## 7. 优化建议（Phase 4.2 候选）

> 每项含：当前问题 / 产生原因 / 推荐方案 / 预期收益 / 涉及文件 / 数据迁移风险 / 实施成本 / 优先级。

### R1 任务列表虚拟滚动（P0）

- **当前问题**：10k 任务时一次筛选 2.6–5.6 s，点击完成 8.2 s。
- **产生原因**：`TasksPage` 一次性渲染全部未完成任务行（约 8,000 个 `TaskRow`），每次状态变化整页 reconcile + layout + paint。
- **推荐方案**：引入轻量虚拟列表（自研窗口化渲染，不新增依赖；或按分组分段窗口化），仅渲染视口 ± 一屏的行；分组滚动采用"分组头 + 行高测量/估算"。
- **预期收益**：筛选/搜索端到端从 2.6–5.6 s 降至 **<200 ms**；勾选从 8.2 s 降至 **<300 ms**（目标值需 Phase 4.2 实测验证）。
- **涉及文件**：`src/features/tasks/TasksPage.tsx`、`src/features/tasks/TaskRow.tsx`（可能新增 `src/components/VirtualList.tsx`）。
- **数据迁移风险**：无（纯渲染层）。
- **实施成本**：M（1–2 人日）。
- **优先级**：P0。

### R2 行组件 memo + 分组/排序缓存（P0）

- **当前问题**：每次渲染重复执行 `sortTasks`（49.5 ms）、分组排序（45.6 ms）与全部行 diff。
- **产生原因**：`TaskRow` 未 `memo`，`TasksPage` 的 groups 在每次输入变化时重建；`sortTasks` 每次拷贝数组。
- **推荐方案**：`TaskRow` 用 `React.memo` + 稳定回调；`useMemo` 缓存 groups（依赖仅 tasks/筛选条件）；减少派生排序次数（一次排序复用于分组）。
- **预期收益**：渲染计算开销降低约 40–60%（基于 88 ms/次的统计成本估算，Phase 4.2 复测确认）。
- **涉及文件**：`TasksPage.tsx`、`TaskRow.tsx`、`src/lib/selectors.ts`。
- **数据迁移风险**：无。
- **实施成本**：S（0.5 人日）。
- **优先级**：P0（与 R1 同批实施）。

### R3 Dashboard 统计单遍聚合（P1）

- **当前问题**：首页每次渲染执行多次全量扫描（10k 时 sort 49.5 + last7 22.6 + focus 13.5 + stats 2.5 ms）。
- **产生原因**：`todayStats`、`last7DayCompletion`、`focusTasks` 各自 `filter` 全量数组。
- **推荐方案**：新增 `buildDashboardStats(tasks)` 单次遍历产出 total/done/open/percent/7 日柱/focus 候选；`useMemo` 按 `data.tasks` 缓存。
- **预期收益**：统计计算从 ~88 ms 降至 ~15–25 ms（10k）。
- **涉及文件**：`src/lib/selectors.ts`、`src/features/today/DashboardPage.tsx`。
- **数据迁移风险**：无。
- **实施成本**：S（0.5 人日）。
- **优先级**：P1。

### R4 搜索防抖 + 结果上限（P1）

- **当前问题**：每次输入触发全量过滤 + 全量渲染（配合 R1 后可缓解，但仍浪费计算）。
- **产生原因**：受控 input 直接驱动筛选。
- **推荐方案**：150–200 ms 输入防抖；结果上限（如先渲染前 200 条 + "查看更多"）；搜索词高亮可选。
- **预期收益**：连续输入时计算次数从"每键一次"降至"每次停顿一次"。
- **涉及文件**：`TasksPage.tsx`。
- **数据迁移风险**：无。
- **实施成本**：S。
- **优先级**：P1。

### R5 任务页默认视图收敛（P1）

- **当前问题**：默认渲染"全部未完成"，大库时首屏 DOM 巨大。
- **推荐方案**：默认展示"今天 + 已逾期 + 即将前 N 条"，其余折叠为"加载更多"（保留现有筛选可查看全部）。
- **预期收益**：首屏渲染行数下降一个数量级。
- **涉及文件**：`TasksPage.tsx`。
- **数据迁移风险**：无。
- **实施成本**：S–M。
- **优先级**：P1（可与 R1 合并交付）。

### R6 写入合并与增量接口（P2）

- **当前问题**：每次提交整份写入（10k 时 33–54 ms/次）；连续操作叠加。
- **产生原因**：`putState` 写整份 `AppData`；`saveAppData` 无批处理/合并队列。
- **推荐方案**：保留整份写入（架构不变），在 `AppStore` 增加"写队列 + 最近 N ms 合并"；对外暴露 `applyMutations`，未来拆分 store 时可直接切换到增量写。
- **预期收益**：连续操作写入次数下降；20 次连续操作写入耗时 1.35 s → 可接近批量参考值 0.50 s。
- **涉及文件**：`src/store/AppStore.tsx`、`src/lib/storage/index.ts`、`src/lib/storage/db.ts`。
- **数据迁移风险**：无（写接口兼容）。
- **实施成本**：S–M。
- **优先级**：P2。

### R7 事务复用 / 批量写（P2，随 R6）

- **当前问题**：每次操作新建事务；批量能力缺失。
- **推荐方案**：提供 `putStateBatch(records)`/复用读事务；仅在确实需要多记录写入时使用。
- **预期收益**：批量写参考值 20 条 0.50 s（现 1.35 s，约 −63%）。
- **涉及文件**：`src/lib/storage/db.ts`。
- **风险/成本**：低 / S。

### R8 生产首屏预加载与骨架（P3）

- **当前问题**：生产重载 10k 中位 192 ms，尚可接受。
- **方案**：首屏骨架 + 预取 `getState`；仅在后续首屏指标变大时实施。
- **风险/成本**：低 / S。**优先级 P3。**

### R9 拆分 Object Store + 索引（P3，暂不实施）

- 见第 8 节结论。**明确不在 Phase 4.2 实施**；触发条件与前置条件见下。

### R10 持久化搜索索引（P3）

- 仅在 R1/R2 后搜索仍不达标（目标 <200 ms）时评估；当前纯计算 15.8 ms，预计不需要。

## 8. Object Store 拆分结论（明确）

**Phase 4.2 不拆分 Object Store，继续使用单文档 `app` store（`state` 记录）。**

依据（10k 实测）：

1. 列表类查询拆分后更慢：未完成查询 **468.5 ms** vs 现状约 **33 ms**；搜索 **219.9 ms** vs **49 ms**；未完成计数 **173.8 ms** vs **35 ms**。
2. 写入成本不可接受：拆分后一次全量写 **4,432.5 ms**，现状 **54.4 ms**（慢约 81 倍，索引维护 + 1 万条 put）。
3. 现有瓶颈（渲染）与存储结构无关；先做虚拟化/缓存，收益数量级更大。
4. 单条更新拆分后确实更快（2.1 ms vs 66 ms），但当前端到端 8.2 s 中写库占比 <1%，优化它没有意义。

**何时重新评估拆分**（需同时满足）：

- 任务量稳定 > 50,000，且产品需要"分页/按需加载"而不是全量视图；
- 已完成 R1/R2/R5（分页/虚拟化已落地），并仍存在由存储结构导致的瓶颈；
- 引入云端增量同步/多设备合并，需要按实体同步与冲突解决（此时拆 store + `updatedAt`/`deletedAt` 字段是前提）；
- 有真实查询分布数据（各查询占比与返回规模）证明"部分读取"优于"整份读取"。

**若拆分，建议方案**（Phase 4.2 不实施，仅记录）：

- `tasks`（主键 `id`，索引 `date`、`completedFlag`(数值)、`projectId`、`updatedAt`）
- `habits`、`habitLogs`（复合主键 `[habitId,date]`）、`settings`（单例）、`meta`
- 迁移：schemaVersion 3；先双写校验（旧单文档 + 新 stores），再切换读取；保留回滚副本。
- 注意：IndexedDB 索引键不支持 boolean，`completed` 必须落为 `completedFlag: 0|1`。

---

## 9. 索引结论

**当前不新增任何索引。** 理由：单文档架构下所有查询都在内存数组上完成，IndexedDB 索引无查询入口；新建索引只会增加写入成本（实测索引维护使 10k 全量写从 54 ms → 4.4 s）。

若未来拆分，按优先级：

| 索引 | 必要性 | 依据 |
|---|---|---|
| `date` | 高 | 日历/今日/周视图按日期取子集（拆分原型 15.9 ms） |
| `completedFlag` | 高 | 待办列表/完成率（需数值字段） |
| `projectId` | 中 | 分类筛选（原型 114 ms，收益有限但业务需要） |
| `createdAt` | 低（仅分页游标） | 原型 cursor 50 条 7.8 ms；当前无分页需求 |

## 10. 分页 / 游标 / 虚拟列表评估

- **虚拟列表：必须做（P0）。** 瓶颈 #1 的直接解法；不需要新依赖，按视口窗口化渲染即可；需要处理分组头、行高估算与滚动定位。
- **分页：任务页需要"加载更多"而不是传统分页**；统计与日历不需要（它们本来只取聚合/子集）。
- **游标查询：拆分 store 后才有意义**（`createdAt`/`date` 游标）；当前单文档读取 33 ms，分页收益 <30 ms，不值得引入。

## 12. 局限与未测项

- headless + `--disable-gpu` 的渲染数据偏悲观（真实有 GPU 的桌面浏览器通常更快），但相对比较有效；移动端未测。
- 仅测试 Edge（Chromium）157；Safari/Firefox 的 IndexedDB 性能未测。
- 开发态重载包含 Vite 未打包 ESM 的模块加载开销，因此另测了生产构建（见 4.3/4.4）；生产重载数据更接近真实用户。
- 一致性测试覆盖 5,000 条规模、5 次；未覆盖强制杀进程/断电、多标签并发写冲突。
- 拆分原型为合成查询（today/open/project/search/count/update/cursor），不代表真实用户访问分布；结论方向明确（列表类查询更慢），但绝对数值仅用于对比。
- 未测量内存占用（JS heap）与长时间运行的内存增长；建议 Phase 4.2 用 `performance.memory`（Chromium）补充。
