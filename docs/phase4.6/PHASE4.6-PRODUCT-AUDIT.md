## 0. 结论摘要

FlowDay 当前处于**「工程质量显著超前于产品完整度」**的状态。

- **工程面**：Phase 4.5 验收基线扎实 —— 231 项逻辑测试、90/14/29/35 套 E2E、25/25 终验综合检查、a11y 35/35、多标签 CAS 一致性、生产构建稳定，运行时依赖仅 3 个。
- **产品面**：存在三个结构性空洞，使其尚不能作为可付费的生产力产品发布：
  1. **分类（项目）能力实质只读** —— 真实新用户无法创建任何分类；
  2. **没有提醒/通知，且不可安装**（无 PWA manifest 与 Service Worker）；
  3. **没有账号与多端同步** —— 换设备即数据孤岛。

**一句话判断**：可以作为「个人每日计划 + 习惯打卡」单机工具直接交付个人试用；**不宜作为正式付费产品发布**。下一阶段的重心应从「工程完备」转向「产品闭环」。

### 2.2 数据模型现状

```ts
Task      { id, title, notes?, date, time?, durationMin?, priority: 1|2|3,
            projectId?, completed, completedAt?, createdAt, source: 'manual'|'ai' }
Project   { id, name, color }
Habit     { id, name, emoji, weeklyTarget, createdAt, archived }
HabitLog  { habitId, date }
Settings  { name, theme, weekStart, aiEnabled, demoData }
AppData   { version: 1, tasks[], projects[], habits[], habitLogs[], settings }
```

模型缺口（直接影响产品表达力）：

- `Task` 无 `recurrence`（重复）、无 `parentId`（子任务）、无 `tags`、无 `reminderAt`、无 `estimate/actual`。
- `Project` 仅 3 个字段，无 description / archived / dueDate / 排序位。
- 全局无用户、设备、同步游标等字段。

### 2.3 存储与一致性现状（技术事实）

- IndexedDB `flowday-db`（`DB_VERSION = 1`），两个 store：`app`（单文档整份 `AppData`）与 `meta`（`sync:v1` 小记录，权威 revision 来源）。
- 保存策略：整份 `AppData` JSON 单事务写入，防抖 **180ms**；写入带 `baseRevision` + `writerId` 做 CAS。
- 一致性：`readStateWithSync` 单事务一致读，避免「revision 与数据跨版本」混合读。
- 备份：JSON 信封 + SHA-256（规范化 data 段）+ 20MB 上限 + 版本号校验 + 原子导入。

## 3. 核心缺口：项目 CRUD 缺失的影响链与根因

### 3.1 代码级证据

- `git grep project/add` → **0 命中**；
- `src/store/reducer.ts` 的 `Action` 联合类型中**没有任何 project 动作**（仅 task/habit/settings/data 四类）；
- `data.projects` 在全部源码中**只被读取**（`TaskEditor` 下拉、`TaskRow` 色点、`ImportPreviewModal` 统计、`data.ts` 示例数据与导入校验）；
- 新用户初始数据为 `projects: []`（**不是**示例数据），因此「分类」下拉只剩「未分类」。

### 3.2 用户影响链

```
新用户首次进入（空数据）
  └─ 创建任务 → 打开「分类」下拉 → 只有「未分类」
      └─ 全站找不到新分类入口
          └─ 所有任务堆积在单一列表
              └─ 任务页只能按日期分组，无法按项目查看
                  └─ 无法回答「这个项目还剩多少」「本周推进了哪个项目」
                      └─ 长期退化为一个巨大的清单 → 用户流失
```

### 3.3 三层后果

1. **功能不可用**：分类仅对「载入示例数据」或「导入含 projects 的备份」的用户可见。真实新用户拿不到该能力 —— 这不是「少一个页面」，而是**一个已展示但无法建立的维度**。
2. **产品定位被锁死**：无项目维度 → Dashboard 与统计无法做「目标/项目进度」→ FlowDay 只能做「日程提醒器」，无法承接「项目制工作者」（付费意愿最高的人群）。
3. **技术债加速累积**：越晚补，需同时补 reducer 动作、表单、路由、批量迁移、导入校验、统计口径，成本越高。

### 3.4 根因分析

| 层级 | 根因 |
|---|---|
| 数据层 | `Project` 是 Phase 4 早期为演示视觉预留的结构，业务动作从未实现 |
| 流程层 | Phase 4.5 验收以「不新增功能」为硬边界，缺口被制度化保留（P2 记录、不处理） |
| 决策层 | 「项目管理」被归为「新功能」而非「既有功能的可用性补全」，导致优先级被系统性低估 |

**建议定性修正**：项目 CRUD 应重新归类为 **P0 缺陷修复**（既有功能不可用），而非 P2 新功能。这是本次评估最重要的分类调整。

## 5. 技术架构评估

### 5.1 结论

**当前架构对「个人单机、任务量 ≤10k」完全够用，不应为技术先进而引入后端/云同步/Worker。** 真正需要立即修的是产品缺口与 PWA 可用性，而非架构升级。

### 5.2 分项评估

| 维度 | 现状 | 判断 | 建议 |
|---|---|---|---|
| 数据组织 | 单文档整份 `AppData` + meta 小记录 | 简单、可测、事务一致；写入成本随数据量线性增长 | 保持；>25k 再评估 |
| 保存策略 | 整份 JSON 单事务 + 180ms 防抖 | 10k 内 245ms 达标；25k/40k 402–462ms | 暂不改；如需优化：按实体分 store 或 append-only 日志 + 周期压缩 |
| 增量写入 | 无 | 25k+ 场景的合理优化，但属架构级改造 | **延后到有真实用户数据**再决策，避免过早复杂化 |
| Worker 序列化 | 无 | 同上；可先做「大对象序列化迁移到 Worker」的低风险实验 | 延后 |
| 多标签一致性 | CAS + revision + writerId + BC/降级 | 已达行业水准，可复用为云端同步的语义基础（revision 列） | 保留并复用 |
| 性能 | 虚拟列表、单遍聚合、`useDeferredValue`、memo、防抖 | 已达 10k 流畅 | 不回退即可 |
| PWA | 无 manifest / 无 SW | **低成本高收益缺口** | Phase 5.0-a 补齐 |
| CSP / Referrer | 无 | 本地单页风险低；引入后端/账号后必须补 | 5.1 前补齐 |
| AI 接入 | 本地规则 mock，接口已预留 `AssistantProvider` | 结构正确，缺真实 provider 与服务端代理 | 5.0-d 实施 |
| 后端必要性 | 无 | 商业化必需；个人工具非必需 | 5.1 再上（Supabase） |

### 5.3 若引入后端：方案对比

| 方案 | 优点 | 缺点 | 成本量级 |
|---|---|---|---|
| **Supabase（推荐）** | Auth/Postgres/RLS/Realtime 一体；RLS 天然隔离；revision 列可直接复用现有 CAS 语义 | 国内访问需代理/加速；免费额度有限 | Pro **$25/项目/月**（含 $10 compute credit） |
| 自建 Node/Postgres | 完全可控、可境内备案部署 | 运维/安全/备份全部自担，开发成本翻倍 | VPS ¥60–200/月 + 人力 |
| Cloudflare（Workers + D1 + R2） | 边缘低延迟、免费额度大、AI 代理方便 | D1 能力弱于 Postgres，复杂查询受限 | 免费–$5/月起 |
| 纯前端 + BYOK | 零后端成本、隐私最优 | 密钥前端风险、无多端、无法做订阅计费 | ¥0 |

### 5.4 AI 成本测算（基于 DeepSeek-V4-Pro 永久价）

官方价格（2026-05-31 起永久生效）：输入缓存命中 **¥0.025/百万 tokens**、输入未命中 **¥3/百万**、输出 **¥6/百万**（来源见 §12）。

| 场景 | 估算 | 月成本/用户 |
|---|---|---|
| 每日 20 次调用、每次 2k 输入（含缓存命中）+ 500 输出 | ~40k 输入 + 10k 输出/天 | **< ¥1** |
| 重度用户（100 次/天） | ~200k 输入 + 50k 输出/天 | ¥3–5 |

结论：**AI 边际成本极低，瓶颈在工程与产品设计**，不在成本。但必须走服务端代理（密钥不落前端）并加限流/额度护栏。

### 6.3 竞品护城河 vs FlowDay 差异化机会

**竞品护城河（FlowDay 目前全部缺失或不足）**：① 提醒/系统通知；② 项目/标签/协作分层；③ 多端同步；④ 一体化（日历+文档+笔记）。

**FlowDay 可守的三个差异化点**：

1. **本地优先 + 隐私**：数据不出设备（现在就是），配合可选「端到端加密同步」—— 对隐私敏感人群（律师/医疗/研究者）有真实价值。
2. **设计品质**：玻璃体系与中文排版已达竞品水准，视觉上不输 Things / Sunsama。
3. **AI 规划（Jing）**：已具备「提案 → 确认 → 执行」的正确交互骨架，比直接对话式 AI 更可控，可做成差异化核心。

## 9. 技术方案与成本分析

### 9.1 25k+ 写入优化对比

| 方案 | 做法 | 收益 | 成本 | 风险 | 建议 |
|---|---|---|---|---|---|
| 维持现状 | 整份写入 + 防抖 | 0 | 0 | 25k+ 仍 402–462ms | 暂时保持 |
| 按实体分 store | tasks/projects/habits 分表，仅写变更表 | 大任务量写入降至 O(变更) | 8–12 人日 | 事务边界复杂，多实体原子性需重组 | 数据量证明需要时再做 |
| append-only 日志 | 记录操作日志 + 周期压缩快照 | 写入最快，天然支持撤销 | 12–15 人日 | 读放大、压缩策略复杂 | 不推荐（过度设计） |
| Worker 序列化 | 把 JSON.stringify 移出主线程 | 消除卡顿感 | 2–3 人日 | 收益有限（受 IDB 写入限制） | 可选实验 |

**结论**：在 25k+ 用户出现前不投入。

### 9.2 PWA 与通知技术要点

- `manifest`：`display: standalone`、`theme_color`、图标集（建议 192/512 + maskable）。
- SW：预缓存应用壳（`index.html` + 入口 JS/CSS），**版本化 + `skipWaiting` 谨慎策略**避免用户长期停留旧版本。
- 提醒：无后端时用「应用内提醒 + 打开时补发」；有后端后用 Web Push（iOS 需安装后才可推送）。
- 降级：通知权限被拒 → 应用内横幅/角标提醒，不得静默失败。

### 9.3 云端同步技术要点（5.1）

- 表结构：`tasks(user_id, id, ..., updated_at, deleted_at, revision)`，以 `revision` 做乐观并发（复用现有 CAS 语义）。
- RLS：`auth.uid() = user_id` 强制隔离，前端不得直连他人数据。
- 同步：拉取 `since_revision` 增量 + 本地待推送队列；冲突沿用现有「三选一 + 草稿」交互。
- 迁移：首次登录时把本地 `AppData` 全量导入，保留 `writerId` 与本地备份回滚点。
- 安全：CSP、`Referrer-Policy: strict-origin-when-cross-origin`、token 不落 localStorage 明文（优先 httpOnly cookie + BFF）。

### 9.4 AI 代理设计（5.0-d）

- 形态：Cloudflare Worker（免费额度）+ DeepSeek API，前端只调代理。
- 输入：用户输入 + 精简上下文（今日任务摘要，≤2k tokens）。
- 输出：结构化 JSON（提案），前端渲染为可确认卡片，禁止直接写库。
- 护栏：单用户日调用上限、单次 token 上限、超限降级为本地规则；日志脱敏。
- 隐私：明确告知「任务文本将发送至模型服务」，提供关闭开关（已有 `aiEnabled`）。

## 11. 六个必答问题

### 11.1 当前是否具备真实用户使用价值？

**有条件具备。** 作为「个人每日计划 + 习惯打卡」的单机工具，功能闭环成立（任务/今日/日历/习惯/备份/多标签安全），可直接交付个人用户日常使用，且体验优于多数免费工具。但作为生产力产品不成立：分类无法创建、无提醒、不可安装、无多端 —— 无法占据 Todoist / 滴答清单的日常位置。

### 11.2 当前最影响竞争力的三个问题？

1. **分类/项目能力实质只读** → 产品无法承载工作流，定位被锁死为「清单」。
2. **无提醒 + 不可安装（PWA 缺失）** → 抓不住「该做的事」，移动端形同浏览器标签页。
3. **无账号与多端同步** → 换设备即数据孤岛，直接排除大多数用户。

### 11.3 下一阶段最值得优先开发的五项功能？

1. **项目 CRUD + 项目页**（F1）
2. **PWA 化 + 提醒通知**（F2 + F3）
3. **重复任务 + 子任务**（F4 + F5）
4. **统计与可视化**（F7）
5. **日历/数据互通（ICS + CSV/Markdown 导出）**（F8 + F9）

账户与云同步（F11）紧随其后（5.1）。

### 11.4 是否有必要引入后端和云同步？

**短期不需要，中期必须。**

- 若定位「本地优先个人工具」：可继续纯前端 + Worker 代理做 AI，零后端成本，隐私最优。
- 若**要商业化**：账号 + 同步是硬门槛（换机丢失是致命体验；免费竞品均支持多端）。
- 建议：不早于 **5.1**，选 **Supabase**（$25/月起），复用现有 revision/CAS 语义，先只做「账号 + 同步」，**不做协作**。

### 11.5 是否具备商业化潜力？

**有条件具备，但风险高。**

- **有利**：市场 CAGR 15.9%；体验与视觉已达竞品水准；「本地优先 + 隐私 + AI 规划」可差异化；Things / Sunsama / Akiflow 证明该品类有付费意愿。
- **不利**：免费竞品强力（MS To Do / Apple Reminders / 飞书）；一体化吞并；月流失 6.5%；ARPU 偏低。
- **可行路径**：免费（本地无限/单设备/无 AI）+ Pro ¥199/年（同步 + AI 额度 + 高级统计）+ 早鸟买断 ¥499。**首年目标应是验证留存而非收入**；早期服务器成本 < ¥500/月。

### 11.6 Phase 5.0 应该如何分阶段实施？

见 §10：**5.0-a 产品补洞 → 5.0-b 任务表达力 → 5.0-c 价值感知 → 5.0-d AI 产品化 → 5.1 云端化**，每阶段设通用门禁 + 专项门禁，任何阶段不达标不进入下一阶段。

### 13.4 术语

- **RICE**：Reach × Impact × Confidence ÷ Effort，用于性价比排序。
- **CAS**：Compare-And-Swap，本文指基于 revision 的乐观并发写入。

- **BYOK**：Bring Your Own Key，用户自备模型 API 密钥。
